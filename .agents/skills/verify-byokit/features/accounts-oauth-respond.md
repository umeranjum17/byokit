# OAuth subscription account respond

A consumer app with two signed-in Grok accounts (device code) asks `Accounts.respond(member, { account, model, context, onText })` and each answer streams through the pinned Pi Models path with that account's own sign-in; a 429 rests only that account, typed and never retried, while the other still answers. A refresh the provider proves revoked (`invalid_grant`) or refuses with a bare 400-403 signs only that account out, while a 5xx or a dropped connection keeps the sign-in, typed `network`: on phones and browsers (`withKeys(portable)`), where the kit refreshes, and on the default computer platform, where Pi refreshes and the kit reads the status Pi's token request was answered with, for `respond` and `keepFresh` alike. A model from another provider and a route the platform cannot run are refused, typed, before any request. All against the built `@byokit/accounts` (`.`, `/keys`, `/testing`), `mockDevice()` and a loopback stand-in for xAI's Responses endpoint that replays `fixtures/conformance/pi-streams.json`. The same path serves GitHub Copilot, Kimi, Meta and MiniMax sign-ins. MiniMax's saved region selects `minimax` or `minimax-cn`; its OAuth token is only the bearer, never `x-api-key`, and its unrefreshable expiry ends `signed_out` with the account reading `needs_again`.

## Sub-features

- `oauth-respond-own-bearer`: `respond` for the bare primary `grok` and for `grok.<id>` each streams the fixture answer (`Hello` into `onText`, the `lookup` tool call, usage `[3, 2, 5]`, `stopReason: 'toolUse'`), and the request reaching `/v1/responses` carries that account's own bearer.
- `oauth-respond-429`: a 429 (with `retry-after: 120`) on `grok.<id>` rejects with `ResponseError` kind `rate_limit`, `status` 429 and `until` about two minutes out; exactly one request went out; `status` shows that account `resting` and the primary `ready`, and the primary still answers.
- `oauth-respond-provider`: a model whose `provider` is not `xai` rejects with `KeyRouteError` code `provider` before any request.
- `oauth-respond-not-included`: Meta's route (`meta:code`, browser `no`) on `withKeys(portable)` rejects with `ResponseError` kind `not_included` before any request, where it used to throw an untyped `Error`.
- `oauth-respond-refused-refresh`: once the primary's sign-in is due and the provider refuses its refresh (`invalid_grant`, 400), `respond` rejects with `ResponseError` kind `signed_out`, sends no request, deletes only that sign-in, and `list` then holds only the other account, still `resting`.
- `oauth-respond-bare-403`: once a fresh sign-in is due and its refresh is answered with a bare 403 and no `invalid_grant` body, `respond` rejects with `ResponseError` kind `signed_out`, sends no request, and deletes that sign-in.
- `oauth-respond-refusal-kept`: once a fresh sign-in is due and its refresh is answered with a 5xx, and again with a dropped connection, `respond` rejects with `ResponseError` kind `network` and that sign-in stays listed.
- `oauth-respond-computer-network`: on the default computer platform, a seeded expired Grok sign-in whose refresh gets no answer inside Pi (the egress guard refusing xAI) rejects with `ResponseError` kind `network`, and the credential is still stored and the account still listed.
- `oauth-respond-computer-signout`: on the default computer platform, a seeded expired Kimi sign-in whose refresh Pi sends to a stand-in token endpoint (`KIMI_CODE_OAUTH_HOST`) answering a bare 403, and separately a 400 `invalid_grant`, rejects with `ResponseError` kind `signed_out` after exactly one refresh, deletes the credential, empties `list`, fires `onExpired` once, and a later `respond` and `keepFresh` send no second refresh; `keepFresh` alone on a fresh such sign-in answered a bare 403 fires `onExpired` once, leaves it not `ready`, and does not refresh it again.
- `oauth-respond-minimax`: sign in global and China accounts with `mockDevice({ dialect: 'minimax', region })`, restart Accounts on the saved store, then stream `Hello` on both the computer and portable entries through the pinned Anthropic Messages adapter. Each loopback region base receives only its own bearer, with no `x-api-key`; a cross-region model is refused before sending. A China 429 rests only China while global still answers; expiring global sends neither a model request nor a refresh, rejects typed `signed_out` and reads `needs_again`. Neither canary appears in any answer, event, error or public account view.
- `oauth-respond-no-token`: neither access token appears in an answer, event, error, `list`, `status` or the store index.

## How to get to it (user POV)

- The app constructs `new Accounts({ deviceBase, offer: ['grok', 'meta'], store }, withKeys(portable))` with `withKeys` from `@byokit/accounts/keys`, signs in two Grok accounts through `add(1, 'grok', { via: 'code' })` and `finished`, and calls `respond(1, { account, model, context, onText })` with a pinned Pi `Model` whose `provider` is `xai`.

## Gotchas

- Use `withKeys(portable)`: on a computer, Pi's own engine signs Grok in against xAI itself, which `mockDevice()` cannot stand in for; the portable engine takes `deviceBase`.
- On a computer, Pi's xAI token address is fixed; drive the refusal through Kimi, whose Pi refresh honours `KIMI_CODE_OAUTH_HOST`. Answer the stand-in with a 4xx, not a 5xx: Pi retries a Kimi 429 or 5xx three times with backoff before it gives up.
- Meta is offered on a portable platform only when the app names it in `offer`; otherwise `respond` stops earlier with `AI account not offered here`.
- After the primary is signed out, the bare `grok` id resolves to the remaining account, so read the outcome from `list`, not `status(1, 'grok')`.
- `mockDevice()` tokens last an hour, so no refresh happens until the drive makes a sign-in due; a rotating refresh spends its grant, and `state.live.clear()` makes the next one answer `invalid_grant`.
- On phones and in browsers the portable engine gives the access token as the key; Kimi's bearer header and Copilot's per-token base URL are derived by Pi's own engine on a computer.
