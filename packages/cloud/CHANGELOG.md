## 0.2.0 (2026-10-18)

- FIX: Cloud setup reports install failures as `installing` on first and resumed attempts while keeping adoption guard failures at `inspecting`.
- FEATURE: A reinstalled app or a new phone can take over its own cloud computer. `setup()` on a computer that already runs the app's own install now ends `failed` with the typed cause `error.ownerEnrolled` (new words that say the person can move it to this phone, and the other phone loses access) instead of the generic `error.app`, and changes nothing. After the person confirms, the same `setup()` with `replaceOwner: true` reinstalls in place (`Machine.adopt` gains `replaceOwner`, which takes over only the kit's own install) and the pair gate's `PairContext` carries `replaceOwner: true`, so `pairEnrol`/`deliverPhoneKey` deliver the key as `OWNER_KEY_FILE` (`owner.bin`). On the machine, `replacePhoneKey(host, key)` revokes every other phone grant and binds the new key in one call, durable across restarts; the host then writes the new phone's receipt. New `MachineErrorCode` `owner-enrolled`; `bindPhoneKey` now rejects with it (was `exists`) when another phone holds the binding.
- SECURITY: Only the provider account can replace the owner phone: the new key arrives only by provider delivery (account key) after the person confirms on the setup device, the host calls `replacePhoneKey` for `owner.bin` only, never for anything a paired device or the network sent, and a `phone.bin` delivery still never replaces an owner. The old phone's grant is revoked before the new key is bound, so a lost phone loses access as soon as its owner re-enrols.
- FEATURE: `setup()` gives the cloud computer its secure address as its own step. With `address: { hostname, port, onStep? }` it emits `securing` (`setup.securing` words) after `installing`: the kit confirms the person's tailnet name, or joins it (`onStep` carries the sign-in link), then privately serves the app's loopback `port` on it (`tailscale serve --tcp`, read back before the step), so a recipe used this way no longer serves its own port.
- FEATURE: `pairEnrol` now ends with a receipt the phone can pair with. After `bindPhoneKey`, the host writes `phoneReceipt(host, key)` to `<workDir>/.byokit/outbox/receipt.json`; `pairEnrol` reads it back as the run user, checks it is for the delivered phone key, and the `pairing` step carries `receipt: { host, device, urls }` (the host's public key, the phone's device on it, and `ws://<tailnet name>:<port>`). The phone opens a real `@byokit/pair` `DeviceLink` with that receipt and its own secret key alone. Breaking for hosts that enrol through `pairEnrol`: they must write the receipt, or the gate fails `timeout` after a minute; a receipt for another phone fails `owner-enrolled`.

## 0.1.0 (2026-10-18)

- FIX: The Boat adapter's 429/5xx retry backoff ends at once when the caller's abort signal fires, and one 10 s deadline bounds the backoff waits and when a new attempt may start, instead of a per-attempt one. The deadline is per request: one request with all its attempts and waits, so a method that sends several requests gets one deadline each. `boat()` takes an optional `signal` that cancels the provider for good (build a new `boat()` for the next operation); an aborted backoff fails `unreachable`, the same typed error an aborted fetch gives, so a caller checking its own aborted signal keeps reading cancel exactly as before. Past the deadline the last answer stands, exactly as when the retries run out (`provider`, or `unknown` from `status`). The retry counts and the 1 s, 2 s, 4 s waits are unchanged; an in-flight request is never cut by the deadline (only the caller's signal cancels it), because a non-detached exec POST legitimately stays open up to its `timeoutSeconds`.
- FEATURE: Link a provider account without pasting a key: `claim({ baseUrl, email })` drives Boat's documented agent sign-in (discover, service_auth register, email claim ceremony, token polling with interval/slow_down/expired handling) as `open-page`, `type-code`, `waiting`, `done` (`key`, `expires`, `scopes`) or one `failed` step, with `claim.refused`/`claim.expired` words.
- FIX: The Boat adapter now speaks the public boat-v1 API instead of the loopback fixture's names. It reads the account id at `user.id`, the created/queried sandbox at `sandbox.id`/`sandbox.state`, the deletion operation at `operation.id`/`operation.status === 'completed'`, a detached command's `processId` and `running`, and a named snapshot's `snapshot.status`; it sends `X-Ascii-Confirm-Delete` and `encoding: 'base64'`; its trial plan maps `sandboxPlanKey: 'trial'`/`subscriptionTrialEndsAt`; and `key`/`why` are absent because the public API has no current-key route and no sandbox stop-reason field. The loopback bench (`src/testing/fake-sandbox-server.ts`) now serves those same public shapes. Adapter and fixture only; no live call, no VM, no spend. It also no longer reports a lost or signal-killed command (`status: 'lost'`, null `exitCode`) as exit 0; that read is a `provider` failure. `sleep` polls the sandbox until it is archived, and the deletion and named-snapshot polls are bounded by a typed `timeout`, with a `blocked` deletion treated as terminal.
- FEATURE: `revokeClaim({ baseUrl, key })` ends a key `claim()` returned (RFC 7009 at the provider metadata's `revocation_endpoint`, the key as client auth); a failure rejects with a `MachineError` naming its cause (`unsupported` when the endpoint is missing, `unauthorized` on 401/403, `provider` with the provider's error code, `unreachable`). The fake sandbox server serves that route: a revoked key answers 401 and a revoked assertion `invalid_grant`.
- SECURITY: A claimed key can now be revoked, and `claim()` no longer leaves the fresh sign-in assertion that arrives beside the key unrevoked: it revokes it before `done`, and if that fails it revokes the key too and ends `failed`.
- FIX: The Boat adapter's one 10 s request deadline still caps the 1 s, 2 s, 4 s retry waits, but a wait it capped now earns the retry it was waiting for. Giving up there returned a transient 429/5xx as a hard `provider` failure after spending the whole budget on the wait, so a provider whose own answers take a second each lost retries it was promised; a slow answer that arrives past the deadline still ends the retries and the last answer stands.
- List existing Boat computers and adopt one after installation consent, without creating another rental; refuse account/identity mismatches and existing installation paths, retaining the ref for install retry.
- First public release, on the npm `next` tag. `claim()` passed a recorded live sign-in against Boat (link, code, key, revoke); create, install and hosting with a claimed key are still unproven until M6, so apps keep `setup.makeKey` for now and `latest` waits for M6.
- Add the Node-only Hetzner Cloud first slice: API-loaded shared sizes and prices, the app's own project/token, create/status/confirmed deletion, an SSH-22-only IPv4 provider firewall with failed-setup cleanup, pinned SSH and unchanged HostRecipe bootstrap. Copies and start/stop remain follow-up work; stopped servers still bill.
- Removing a machine destroys its server before sweeping unused kit-labelled firewalls, even if its firewall was detached or changed. SSH exec/write/hostKey still refuse an unsafe firewall with typed re-attach-or-remove guidance.
- Retry a timed-out private-network status check within the existing sign-in window; a slow check no longer ends phone sign-in early. A window that stays hung ends with the join deadline wording, while standalone status checks retain their timeout error.
- FEATURE: `status(m, { app, label })` is the one read a phone polls through create, install, stop, start and delete: it resolves `{ machine, host, words }`, asks the host only while the machine is on (so no command reaches a machine that is still being set up or is asleep), and gives the one plain sentence to show. The fakes now model the real provider more closely: `fakeProvider({ createReads })` and the loopback Boat server's `slowCreateReads` keep a new machine `creating` for a few reads, as Boat's create resolves before the machine is on; both restart enabled units on every wake (a wake is a cold boot); a command sent to a fake machine that is not on fails `unreachable`; and a removed fake machine reads `gone` instead of `on`.
- FEATURE: Saved copies, reset and disk space for the cloud computer (spec 4.4, 5.10). `snapshots()` lists the kit's own saved copies of the machine, newest first; `snapshot({ keep })` saves one and, only after the provider lists it ready, deletes the oldest of this machine's copies past `keep` (a failed delete is reported as `pruneError` on the saved copy, not thrown) (default 3, inside Boat's 10 free copies; a copy the kit did not make is never touched); `scheduleSnapshots({ everyMs, keep, onResult })` saves a copy when the newest is older than `everyMs`, on a timer while the app runs (returns `{ stop() }`; no hosted scheduler; each check follows the previous one, so a daily schedule saves daily); `restore(id)` rebuilds the machine from one copy as a new machine with the same name and tailnet identity, saves the new ref before the old machine is deleted (a replacement that never comes on is deleted; an old machine that will not delete is retried, then reported as possibly billing), and rejects the typed `no-snapshot` for a copy that is gone; `disk()` reads `{ usedGb, totalGb }` from `df` on the machine. New words `snapshot.restore` (says what a reset loses), `disk.used` and `error.noSnapshot`. Boat implements it; the SSH VM adapter and a machine made with `keepCopies: false` reject `unsupported`. A save past Boat's 10 free copies with no credit rejects `balance` (`cost.balance` words) and deletes nothing. One save, reset or remove runs at a time per machine store: another one meanwhile rejects the typed `busy` and changes nothing. A reset of a `failed` machine skips the stop step and builds from the copy. `scheduleSnapshots` resolves its handle and rejects at creation (`bad-recipe`, `no-machine`, `unsupported` for a machine without copies). `disk()` reports decimal GB (bytes / 1e9).
- Enrol exactly the one authenticated phone on a cloud computer: `deliverPhoneKey` hands its 32-byte public key to the machine through provider delivery, `bindPhoneKey` binds it with `Host.enrol` (first phone wins, restart-safe, any other key refused), and `pairEnrol` is the `setup()` `pair` gate behind the existing `pairing` step; the key never travels in `run.env`, `run.argv`, logs or error text.
- SECURITY: New Tailscale installs use pinned 1.104.1 amd64/arm64 static releases with SHA256 verification before extraction or installation; mismatches refuse without installing, replacing the unpinned root installer script.
- Add keyless Boat `joinTailnet()` and `tailnet()`, with phone sign-in steps and userspace networking when no TUN device is present. Join keys are refused until a credential-safe transport exists.
- SECURITY: No public app port by default; bootstrap never calls provider hosting. Explicit `url()` makes a port public. Advertise the person's own tailnet name instead.
- `joinTailnet` emits an `approve` step when the tailnet must approve the machine (`needs-approval`), with or without a sign-in link; its timeout says approval is needed when approval is the block, says the sign-in link expired only when one was shown and the daemon still needs login, and otherwise says it took too long.
- `tailnet()` reports `starting` while Tailscale is still starting, and `joinTailnet` waits through it inside its five-minute deadline before `tailscale up`.
- Report one existing-computer connect as a step stream (checking-access, listing, inspecting, installing, pairing, ready, or failed with the step, a words cause and retryable), each step emitted after its real result; a retry resumes at install on the saved machine, and adopt forwards install lines.
